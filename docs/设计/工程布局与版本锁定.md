## 1. 固定工程布局（构建门禁依赖，不得更改）

**[契约]** 以下路径由 Workflow 脚本的构建门禁**编译期写死**，任何代理不得移动或重命名：

| 路径 | 角色 | 说明 |
| --- | --- | --- |
| `<root>/settings.gradle.kts` | Gradle 工程根 | **工程根 = 当前工作区根** `D:\PROJECT_ZZZZZZZZZ\todo1010` |
| `<root>/build.gradle.kts` | 根构建脚本 | 只声明插件 `apply false` |
| `<root>/gradle/libs.versions.toml` | 版本目录（唯一版本真相） | 所有依赖版本只在此声明 |
| `<root>/gradle/wrapper/gradle-wrapper.{properties,jar}` | wrapper | `distributionUrl` 锁定 Gradle 版本 |
| `<root>/gradlew.bat`、`<root>/gradlew` | wrapper 入口 | 门禁通过 `gradlew.bat` 调用 |
| `<root>/app/` | 唯一 Android 应用模块 | 包名 `app.arttodo` |
| `<root>/rust/Cargo.toml` | Rust crate 清单（**单 crate**） | 见 §1.1 |

| **`<root>/app/build/outputs/apk/debug/app-debug.apk`** | 调试 APK 固定输出 | 门禁读取此路径 |

### 1.1 F1 修正：采用单 crate 布局（`rust/src/**` 承载实现）

v1.0 把 `rust/` 声明为"同时是 package 与 workspace 根 + `rust/src/lib.rs` 仅作再导出 shim + 真实实现在 `rust/crates/domain/`"。该布局**跑不过 v1.0 自己写下的门禁命令**。独立评审复现：`cargo test --manifest-path rust/Cargo.toml --test occurrences` 报 `error: no test target named 'occurrences' in default-run packages / help: available test in 'arttodo_core' package`；整包 `cargo test` 报 `error[E0432]: unresolved import 'arttodo_core'`（根 package 未声明该依赖）→ 均 EXIT=101。

**[契约] v2.0 决定：`rust/` 是单 crate，真实实现就在 `rust/src/**`。** 不再引入 `rust/crates/**`。这样任务书规定的 `rust/src/**` 路径**就是**实现所在，脚本的存在性检查与门禁命令同时成立。

`rust/Cargo.toml`：

```toml
[package]
name = "arttodo_core"
version = "0.1.0"
edition = "2021"

[lib]
name = "arttodo_core"
crate-type = ["cdylib", "lib"]        # cdylib 供 UniFFI;lib 供集成测试引用

[dependencies]
jiff = "0.2"
uniffi = { version = "=0.32.2", features = ["cli"] }
thiserror = "2"

[[bin]]                                # 绑定生成器，crate 内自带
name = "uniffi-bindgen"
path = "src/bin/uniffi-bindgen.rs"

[profile.release]
panic = "unwind"                       # 强制，见《架构契约》§10
```

**[实测] E3 逐字复验**（在 `D:\tmp\rev2` 按上表搭建后运行）：

| 命令 | 结果 |
| --- | --- |
| `cargo test --manifest-path rust/Cargo.toml --test occurrences` | `1 passed`，**EXIT=0** |
| `cargo test --manifest-path rust/Cargo.toml` | EXIT=0 |
| `cargo fmt --manifest-path rust/Cargo.toml --check` | EXIT=0 |
| `cargo clippy --manifest-path rust/Cargo.toml --all-targets -- -D warnings` | EXIT=0 |
| `cargo build --manifest-path rust/Cargo.toml --release` | EXIT=0，产出 `rust/target/release/arttodo_core.dll` |
| 绑定生成（cwd=`rust/`） | EXIT=0，产出 `app/arttodo/core/arttodo_core.kt`，含 `func dayBounds(year: Short, month: Byte, day: Byte, tz: String): Long`（:1116） |

**[契约] 代价与边界**：单 crate 意味着领域代码、UniFFI 导出、绑定生成器同处一个 crate。若日后需要拆多 crate，**必须同时**更新本文件与《AC覆盖表》的全部门禁命令，并重新逐字复验——不得只改布局不改命令（这正是 F1 的成因）。

**[契约] 不提交的路径**：`local.properties`、`rust/target/`、`app/build/`、`app/src/main/jniLibs/`（构建生成）、`*.keystore`、任何凭据。

**[契约] Room schema 例外**：`app/schemas/**/*.json` 必须**提交入库**（迁移测试与备份兼容性的依据）。

## 3. 唯一修改负责人（并行开发的硬约束）

**[契约]** 以下共享点**各自只有一个负责人**。其他代理**不得直接编辑**，只能向负责人提交改动请求（接口变更走《架构契约》的 IDL 评审）。

| 共享点 | 唯一负责人 | 包含文件 | 变更规则 |
| --- | --- | --- | --- |
| **Gradle 根配置** | `engine-build` | `settings.gradle.kts`、`build.gradle.kts`、`gradle.properties`、`gradle/libs.versions.toml`、`gradle/wrapper/**`、`gradlew*`、`app/build.gradle.kts` | 任何依赖版本、ABI、签名、`ksp` 参数、`jniLibs` 源目录的改动必须由 `engine-build` 执行；其他代理以"请求"形式提出 |
| **Room schema 与迁移** | `data-room` | `app/schemas/**`、`app/src/main/java/app/arttodo/data/**`（`*Entity`、`*Dao`、`AppDatabase`、`*Migration`） | 表结构、索引、`version` 递增、迁移体、schema JSON 只由 `data-room` 改；其他代理不得新增/改名列 |
| **导航入口** | `ui-navigation` | `app/src/main/java/app/arttodo/nav/**`、`MainActivity.kt` 中的 `NavHost` 与路由常量、底部栏目的地定义 | 路由字符串、参数契约、深层链接只由 `ui-navigation` 改；页面代理只实现自己的 composable，不改图 |
| **UniFFI IDL / 接口契约** | `ffi-contract` | `rust/uniffi.toml`、`rust/src/**` 中所有 `#[uniffi::export]` 与 `#[derive(uniffi::…)]` 声明、`app/src/main/java/app/arttodo/domain/bridge/**` 的接口定义 | 命令、事件、错误枚举的任何增删改只由 `ffi-contract` 执行；Rust 实现代理不得私自加导出函数 |

**补充的单一负责人**（避免次要冲突）：

| 共享点 | 唯一负责人 |
| --- | --- |
| `app/src/main/assets/art/**` 与 `art_asset` 权利清单 | `art-assets` |
| `app/src/main/java/app/arttodo/system/**`（前台服务、通知通道、时钟采样） | `android-system` |
| `app/src/test/**` 的共享测试夹具与合成数据生成器 | `qa-harness` |
| `docs/设计/**` 的本三份契约文件 | `architect`（仅架构代理可改） |

**[契约] 并行的正确用法**：并行只用于**互不重叠的文件**与**已商定的接口**。`ffi-contract` 必须先冻结 IDL，`rust-domain` 与 `data-room` 才能独立推进；`ui-navigation` 先冻结路由表，`ui-compose` 才能分页面并行。

## 4. UniFFI 生成与 `.so` 打包

### 4.1 已实测的生成链路（单 crate 布局，F1 修正后复验）

以下步骤在 `D:\tmp\rev2` 的**单 crate 等价结构**上**实际执行过**（E3/E4）：

| 步骤 | 命令（cwd） | 实测结果 |
| --- | --- | --- |
| 1. 构建宿主 cdylib | `cargo build --manifest-path rust/Cargo.toml --release`（`<root>`） | EXIT=0，产出 `rust/target/release/arttodo_core.dll` |
| 2. 生成 Kotlin 绑定 | `cargo run --release --bin uniffi-bindgen -- generate --library target/release/arttodo_core.dll --language kotlin --no-format --out-dir <out>`（**cwd 必须在 `rust/`**） | EXIT=0，产出 `<out>/app/arttodo/core/arttodo_core.kt`（1131 行），含 `func dayBounds(...)`（:1116） |

**[契约] 三条必须遵守的实测约束**：

1. **library 模式必须在 crate 目录（含 `Cargo.toml`）内运行**。在 `<root>` 执行时实测失败：`` error running cargo metadata … `cargo metadata` exited with an error: error: could not find `Cargo.toml` `` → exit 1。因此 Gradle 任务必须把 **workingDir 设为 `<root>/rust`**。
2. **`uniffi.toml` 必须位于 crate 根即 `<root>/rust/uniffi.toml`**。放在该处时实测生效（`package app.arttodo.core`，:6）；错放位置会被忽略并回落到默认包名 `uniffi/arttodo_core/`。
3. **生成绑定用 `--no-format`**。不加时实测输出 `Warning: Unable to auto-format arttodo_core.kt using ktlint: Error { kind: NotFound, message: "program not found" }`（本机无 ktlint）；加 `--no-format` 后无警告。断言不得把该警告当失败，也不要为此安装 ktlint。

### 4.2 原生库加载方式（决定 `.so` 命名）

**[实测]** UniFFI 0.32.2 生成的 Kotlin 使用 **JNA 直接映射**，而不是 `System.loadLibrary`：

```kotlin
// arttodo_core.kt:389-395
private fun findLibraryName(componentName: String): String { … return "arttodo_core" }
// arttodo_core.kt:671
Native.register(IntegrityCheckingUniffiLib::class.java, findLibraryName(componentName = "arttodo_core"))
```

**[契约]** 由此推出三条打包要求：

1. 库名必须与 `uniffi.toml` 的 `cdylib_name`（默认 = crate 名 `arttodo_core`）一致，落地为 `libarttodo_core.so`。
2. `.so` 必须位于 APK 的 `lib/<abi>/` 下，JNA 才能在 Android 上解析到。
3. `net.java.dev.jna:jna:<v>@aar` **必须**以 aar 形式依赖，否则 `libjnidispatch.so` 不会进 APK。**[实测]** 依赖 JNA 5.19.1（aar）后 APK 内出现 `lib/arm64-v8a/libjnidispatch.so`（176,520 字节）与 `lib/x86_64/libjnidispatch.so`。

**[契约] 绑定生成的目标库选择**：默认从**宿主 cdylib** 生成（免 NDK、可离线、可复现）。Android `.so` 只用于打包。构建脚本**必须**额外断言宿主库与各 ABI `.so` 导出的 `uniffi_*` 符号集合一致（`nm`/`dumpbin` 比对），防止宿主与目标产物不同步。

### 4.3 `.so` 的 Android 交叉编译（本机阻塞）

| 项 | 状态 | 证据 |
| --- | --- | --- |
| `cargo-ndk` | **未安装** | `which cargo-ndk` → `no cargo-ndk in (…)`；crates.io 最新为 4.1.2（`rust_version` 要求 1.86） |
| Android rust target | **0 个已安装** | `rustup target list --installed` → 仅 `x86_64-pc-windows-msvc` |
| NDK | **不存在** | `ls -d "E:/Android/Sdk/ndk"` → `No such file or directory` |
| SDK 许可 | **7/7 未接受**，`licenses` 目录不存在 | `sdkmanager --licenses` → `7 of 7 SDK package licenses not accepted.` |
| 交叉编译实跑 | **失败** | `cargo build --release --target aarch64-linux-android` → exit 101（target 未安装） |

**[契约] 打包管线**（可解除阻塞后执行）：

```
cargo ndk -t arm64-v8a -t x86_64 -o app/build/generated/jniLibs build --release
# 产物：app/build/generated/jniLibs/{arm64-v8a,x86_64}/libarttodo_core.so
```

并在 `app/build.gradle.kts` 注册：`sourceSets["main"].jniLibs.srcDir("build/generated/jniLibs")`（由 `engine-build` 唯一修改）。Gradle 任务顺序：`cargoNdkBuild` → `generateUniffiBindings` → `preBuild`。

**[未验证]** `cargo-ndk` 在本机的实际行为、NDK 版本选择、各 ABI `.so` 是否真能被 Android 加载 —— 全部未运行。

### 5.3 为什么不是 Gradle 8.11.1（任务书列出的本机版本）

任务书列举了 "Gradle 8.11.1"。**本契约锁定 8.13**，理由链如下（每步都有本轮实测或官方原文）：

1. Room 2.8.5 的代码生成依赖 **KSP**；而 KSP 2.3.12（当前最新稳定线）的 release note 明确 **将最低支持的 AGP 提升至 8.12.0**。
2. AGP 8.12 官方兼容表要求 **Gradle ≥ 8.13**。
4. 本机 `gradle-8.13-bin` **已在 wrapper 缓存中**（目录名 `5xuhj0ry160q40clulazy9h7d` 与 base36(md5) 公式实测吻合，且有 `.ok` 标记），因此升级**不产生下载**。

**[契约] F11 修正：本机 wrapper 缓存只有 `gradle-8.13-bin`，不要按"8.11.1/8.7 已缓存"做假设。** 本轮实测 `ls -1a "E:/caches/gradle/wrapper/dists/"` 的输出**只有** `CACHEDIR.TAG` 与 `gradle-8.13-bin`；`ls -d …/gradle-8.11.1-bin` 与 `ls -d …/gradle-8.7-bin` 均返回 `No such file or directory`。（《环境与工装预检》第 106/440 行列出的三个缓存目录与本次实测不符；本文件与《架构契约》E5 以本次实测为准。该目录此前可能确有三个条目，现已不存在——凡依赖该假设的离线门禁都要按此重算。）

**拒绝的替代（方案 A，未构建验证）**：AGP 8.10.1 + Gradle 8.11.1 + Kotlin 2.2.21 + KSP `2.2.21-2.0.5`。它能在本机已装的 Gradle 8.11.1 上跑，但把 Kotlin 从 2.4.20 降到 2.2.21（落后两个 minor），且 **本轮未实测其可构建**。既然 8.13 已缓存，方案 A 没有收益，**不采用**。

**拒绝的替代（方案 C，追最新）**：AGP 9.4.1 需要 Gradle 9.6.0（本机未缓存）+ build-tools 36.0.0（本机没有）+ KGP 2.4.20 支持 AGP 上限仅到 9.3.1 → 三重冲突，**不采用**。

## 6. minSdk / targetSdk / ABI 的依据

### 6.1 minSdk = 26

**依据一：依赖下限（实测 AAR/artifact 元数据，取最大值）**

| 依赖 | 最低 API | 来源 |
| --- | --- | --- |
| `compose ui-android 1.11.4` | **23** | AAR `AndroidManifest.xml` → `minSdkVersion="23"` |
| `room-runtime-android 2.8.5` | **23** | AAR manifest `minSdkVersion="23"`；官方 release note「minSDK 由 API 21 升至 API 23」 |
| `compose runtime-android 1.11.4` | **23** | AAR manifest |
| `core-ktx 1.18.0` | **23** | AAR manifest |
| `activity-compose 1.13.0` | **23** | AAR manifest |
| `lifecycle-runtime-compose 2.10.0` | **23** | AAR manifest |
| `navigation-compose 2.9.8` | 21 | AAR manifest |
| `material3 1.4.0` | 21 | AAR manifest |
| **实测下限（最大值）** | **23** | |

**依据二：本应用必需的平台 API**

| 能力 | 最低 API | 来源 |
| --- | --- | --- |
| 通知渠道（`NotificationChannel`） | **26** | 官方通知渠道页：「Starting in Android 8.0 (API level 26), all notifications must be assigned to a channel.」本应用必须发长期前台通知与到点通知 |
| `Context.startForegroundService()` + 5 秒内 `startForeground()` | **26** | 官方 Oreo 后台限制页：Android 8.0 起后台应用不能创建后台服务，需 `startForegroundService()`，5 秒内必须 `startForeground()`，否则 ANR |
| `PBKDF2WithHmacSHA256`（可选密码备份 KDF） | **26** | 官方 `javax.crypto.SecretKeyFactory` 页面：`PBKDF2WithHmacSHA256` 为 **API 26** 新增；低于 26 抛 `NoSuchAlgorithmException` |

**结论 [契约] minSdk = 26**：由"依赖下限 23"与"前台服务/通知渠道/PBKDF2 三重 API 下限 26"取上界。选 26 得到**统一的**前台服务与通知语义，避免为 API 23–25 维护一条更不可靠的降级分支。

**诚实边界**：任务的另一半分依据是"目标设备"。**本机 `adb devices -l` 无任何设备**（实测仅打印表头），唯一 AVD 属他项目，因此**"26 能否覆盖目标用户设备分布"未经实测**。若后续真机矩阵显示需支持 API 23–25，改动代价为：加 `NotificationChannel` 的版本分支、前台服务降级路径、KDF 换 `PBKDF2WithHmacSHA1`（API 10+）或引入 desugaring。**该改动必须作为规格变更评审，不得静默调整。**

### 6.2 targetSdk = 36 / compileSdk = 36

- **targetSdk 36**：Google Play 官方 target-sdk 要求页原文「Starting August 31 2026: New apps and app updates must target Android 16 (API level 36) or higher」。今天 2026-10-05，要求已生效。规格要求"开发注意未来商店规范"，取 36 即满足当前与近期要求。
- **compileSdk 36**：本机仅装 `platforms;android-36`（实测 `ls -1 E:/Android/Sdk/platforms` → `android-36`；`android-35` 不存在），且 AGP 8.12 最高支持 API 36。两者一致，无选择余地。
- **[契约]** 不得把 `targetSdk` 写成 35 以下：那会同时违反 Play 现行要求并触发 lint/一致性问题。

### 6.3 ABI = `arm64-v8a` + `x86_64`

| ABI | 依据 |
| --- | --- |
| **arm64-v8a** | 真实 Android 手机的主力 ABI；不声明它等于放弃真机。JNA 5.19.1 aar 内含 `jni/arm64-v8a/libjnidispatch.so`（实测列表） |
| **x86_64** | 本机**唯一**的模拟器系统镜像是 `system-images;android-35;google_apis;x86_64`（`sdkmanager --list_installed` 实测），其 `config.ini` 为 `abi.type = x86_64`。不声明 x86_64 则本机无法做任何模拟器验证 |

**[契约] 排除的 ABI 及理由**：`armeabi-v7a` / `armeabi` / `x86` / `mips*` —— 本机无 32 位设备或镜像，且没有可验证的 32 位目标；声明无法测试的 ABI 违反规格第 8 节"发布构建只包含声明支持且实际测试的 ABI"。

**[实测]** `ndk { abiFilters += listOf("arm64-v8a", "x86_64") }` 下构建成功，APK 内仅出现这两个 ABI 的 `lib/<abi>/*.so`。

**[契约] 后果告知**：仅 32 位的老旧设备将无法安装。这是**有意的取舍**，须在交付报告中如实写明，不得描述为"支持全部 Android 设备"。

### 6.4 32 位与 16 KB 页大小（前瞻，非本轮范围）

**[未验证]** Android 16（API 36）起的 16 KB 页大小对齐要求、以及 Play 的 64 位要求细节，本轮未核对官方文档，也未验证 `.so` 的页对齐。实施 P3 前须核对并可能需要在 NDK 链接参数中显式设置对齐。**本轮不作为已通过项。**

## 7. 门禁命令（脚本可编译期写死）

全部为本轮**实测可用**（E3/E4/E7/E13）。**[契约] 命令必须与 §1.1 的单 crate 布局一致；改布局漏改命令即为 F1 的成因。**

```bat

gradlew.bat --no-daemon assembleDebug
:: → app\build\outputs\apk\debug\app-debug.apk

:: Kotlin 单元测试（含 Robolectric；无需设备）
gradlew.bat --no-daemon testDebugUnitTest

```

```bash

cargo test   --manifest-path rust/Cargo.toml --test <name>
cargo test   --manifest-path rust/Cargo.toml
cargo fmt    --manifest-path rust/Cargo.toml --check
cargo clippy --manifest-path rust/Cargo.toml --all-targets -- -D warnings

:: [N1 修正] panic 策略门禁：必须断言输出为 panic="unwind"，否则门禁失败
:: 必须带 --lib：本 crate 同时有 lib 与 bin(uniffi-bindgen) 两个目标

```

**[实测] E3/E16 逐字复验**（`D:\tmp\rev2`、`D:\tmp\finalcheck`，单 crate 布局）：`--test occurrences` → `3 passed`，EXIT=0；整包 `cargo test` → 4 个 `test result: ok`；`cargo fmt --check` → EXIT=0；`cargo clippy … -D warnings` → EXIT=0。

**[契约] N1 修正——panic 门禁的命令形态（三种形态全部实测）**：

| 形态 | 结果 |
| --- | --- |
| `cargo rustc --manifest-path rust/Cargo.toml --release **--lib** -- --print cfg` | **可用**：输出 `panic="unwind"`，EXIT=0；把 `[profile.release] panic` 改成 `abort` 后同一命令输出 `panic="abort"`，**门禁真的会失败**；在 fresh（无改动）crate 上连续两次运行都稳定输出 |
| `cargo rustc --release -- --print cfg`（**无 `--lib`**） | **在本布局下报错**：`error: extra arguments to 'rustc' can only be passed to one target, consider filtering the package by passing, e.g. --lib or --bin NAME to specify a single target`。因为 §1.1 的 crate **同时有 lib 与 bin**（`uniffi-bindgen`） |
| `cargo rustc --release --print cfg`（**省略 `--`**） | **不可用**：`error: the print flag is unstable, and only available on the nightly channel of Cargo, but this is the stable channel`，EXIT=101 |

**[契约] 为什么必须补这条、且必须带 `--lib`**：§1.1 强制 `panic = "unwind"`，而《架构契约》§10 的"Rust panic 不跨 FFI"保证**完全依赖**该设置（实测：`panic="abort"` 下同一 FFI 调用会终止宿主进程）。v2.0 列出的四条 cargo 命令**没有任何一条**能因 profile 被改坏而失败，该强制项当时处于无门禁状态；而只补 `--print cfg` 却漏 `--lib`，又会因本 crate 的两个目标而直接报错。生产 `scripts/cmd/` 必须使用上表第一行并解析其输出。

**[契约] 环境前置**（脚本首次运行前必须成立）：

1. `JAVA_HOME=E:\devtools\jdk-17`；`ANDROID_HOME=E:\Android\Sdk`。
2. **不创建 `local.properties`**：实测本机可用 `ANDROID_HOME` 完成构建；而写入 `sdk.dir=E:/Android/Sdk` 会让 `lintDebug` **失败**（lint 报 `PropertyEscape` 错误：Windows 路径必须转义为 `E\\:/Android\\/Sdk`）。若确需该文件，由 `engine-build` 用正确转义写入并加入忽略列表；否则 `lintDebug` 会红。
3. `GRADLE_USER_HOME=E:\caches\gradle`（含镜像 init 脚本与 8.13 wrapper 缓存）。
4. 首次 `assembleDebug` 需联网（aliyun 镜像）拉取依赖；此后应通过依赖校验和文件与 Gradle 缓存离线复现。

**[契约] N11 修正——构建证据的可复验性**：本轮全部实测都在 `D:\tmp` 的临时探针工程里完成，且**这些目录已在产出文档后删除**（`D:\tmp\rev2`、`D:\tmp\agptest`、`D:\tmp\rev2-verify` 等，`ls -d` 均 `No such file or directory`）。因此本文件所列的实测结论**目前无法由第三方就地复验**：复验需按 §1.1 重建等价工程，或等产品工程建立后按 `scripts/cmd/` 的脚本在本工作区内复跑。**不得把本文件的单方记录当作第三方已验证的通过项。** 阶段 C 起，所有门禁脚本必须落在工作区 `scripts/cmd/`，使第三方可直接复验。
