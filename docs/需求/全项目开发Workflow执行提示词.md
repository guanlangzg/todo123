## 开始执行

你是本项目的**长任务开发总协调者**。请实际使用 ZCode 的动态 Workflow（`CreateWorkflow`）组织多名子代理，在项目规定的规格与视觉审阅关卡放行后，把当前工作区内的个人艺术 Todo 开发成**可安装、可操作、离线可用的 Android 首版**。用户提交本文授权启动调研、准备、设计、审核与后续获准的实现工作；`CreateWorkflow` 的脚本确认本身不代表用户已经认可需求规格、高保真视觉稿或素材授权。完成可审阅材料之前持续推进；遇到项目明文要求的用户整体审阅，提交明确的审阅包并停在该关卡，获真实用户放行后继续同一工作流或修订运行，不能把后台通知、脚本确认或代理评审视为用户批准。其余常规架构、配色、实现顺序和可逆开发操作无需逐项提问。不要自动发布、购买、注册商店账户、处理真实用户数据、生成/记录生产签名凭据、提交或推送 Git。

用户希望最终实施 P0–P3 的**首版**，但本次提交只表示启动流程，不能越过需求规格的整体审阅。现有 `AGENTS.md`、`memory.md` 限制在“未获用户批准，不进入实现”；在获得规格与视觉关卡的真实确认后，才将项目阶段说明更新为实施中，并搭建代码。后期本地上传图片、手动换图、离线随机管理以及在线图源不属于首版。不要以“AI 开发速度”为理由降低 Rust 参与度、原生界面品质、统计准确性或备份安全性。没有现成产品代码时从零建立工程；不得假装已有 APK 或测试通过。

### 2. Workflow 创建与运行约束

1. 先载入 `dynamic-workflows` 技能，核对 `ListSavedWorkflows` 与 `ListModels`，用 `CreateWorkflow` 启动有阶段关卡的动态 Workflow；设置 `subagent_model: "fe57f340-45cf-4396-a0f2-9faa7217bbe2/ocg/deepseek-v4.1-flash$max"`。若存在**功能范围、模型和审阅关卡均匹配**的已保存工作流，以 `CreateWorkflow({ saved: ... })` 复用；否则编写新的 TypeScript 脚本。无论选择哪种，未要求限制并发，不传 `max_concurrency`；由运行时适配供应商并发，不自行改用其他模型。Workflow 脚本采用用户能理解的中文 `phase(...)` 阶段名、唯一且稳定的子代理名、中间 `report(...)` 进度和最终可打开的主报告 artifact；对两道审阅关卡分别发布可读的待审材料 artifact，不要把待审文档和整份源码都塞进返回值。新脚本先用 `EvalWorkflowSnippet` 验证非代理部分的文件匹配、命令门禁和结果解析；该片段工具不能测试 `agent()`、`phase()` 或发布 artifact。编译失败则修正返回的草稿文件并用 `path` 重提；已运行脚本需要修订则用 `AmendWorkflow`，不重复贴全文或另开运行。
2. 子代理可以负责领域核心、Android 平台与数据、原生 UI/艺术资源、备份和独立评审，但**并行只用于互不重叠的文件与已商定的接口**。先由架构代理产出可测的 Kotlin↔UniFFI↔Rust 契约、事件和存储模式，独立代理审核模型；然后按模块分工实现。对共享文件（Gradle 根配置、Room schema、导航入口、FFI IDL）指定唯一修改负责人，避免并行覆写。各阶段产出实际文件路径与阻塞项，不把完整文件内容塞进跨代理返回值。
3. 计划/关键实现由未参与作者工作的代理独立复审；易错主张通过实际命令或独立复现确认。关键失败修复最多做有界的诊断—修复—复测循环，例如三轮；同一方法两次失败先查根因、换本质不同的方案。若运行中的脚本需要修正，编辑草稿后 `AmendWorkflow`，不要开启新 Workflow 丢失已完成工作。供应商认证/模型级错误不能伪装成测试失败；不可通过门禁应明确升级为阻塞，而不是伪造结果或删测试。**人审关卡的具体做法**：先让制作代理完成工作区待审材料并返回路径；脚本发布该文件 artifact；之后用**独立的一次**代理 `ask` 升级真实阻塞问题，主会话将已发布的材料交给用户。此时问题保持待回答，不因时间过去而默认为通过；只有收到真实用户答复，主会话才用 `ResolveWorkflowQuestion` 原意转达。脚本据实际答复继续、修订或标记受阻；若运行此前已结束，保留完成成果并用 `AmendWorkflow` 续做。不得让尚未返回的制作代理在自己的 `ask` 内先升级问题，否则脚本无法拿到路径并发布审阅材料。不要用无上限轮询等待用户，也不要自行生成“已批准”结果。
4. 所有工作在本工作区进行。**上次检查时**目录只有需求文档和记忆、没有 Gradle/Cargo 工程，也不是 Git 仓库；该状态可能变化，运行时重新枚举文件、工程入口与 Git 状态，依本次证据决定是沿用现有工程还是新建。`git.*` 观察失败需回退到 `files.glob`，不要假设已有分支或 worktree，不自动 `git init`、commit、push。根目录已有资料不得覆盖；构建产物、源代码、可重跑验证脚本与报告清楚分层。凭据绝不写入项目、日志或报告。真实用户数据和非必要个人信息不用于测试；使用合成样例。
5. 预检实际环境而不猜版本。先查 SDK、JDK、Gradle、NDK、Rust Android targets、现有 AVD/USB 设备及许可证状态，并核对当时的 Android/Compose/Room/UniFFI/Rust 官方文档与依赖版本。上次检查检测到 Android SDK（`E:\Android\Sdk`）、JDK 17、Gradle、Rust、API 35 AVD，但未连接设备；这只是快照，以本次运行为准。**现有 AVD 不等于可随意覆盖的空白测试设备**：先辨识用途和安装数据；只有本项目专用的测试 AVD、专用测试包名或另建隔离环境才可安装/执行破坏性恢复、升级、卸载、清除应用数据等测试。若无法建立隔离环境，相关 AC 标记“受阻”，不能改用现有不明环境。新建 AVD 如需用户接受 SDK 许可先交由用户处理。Android emulator MCP **不在 Workflow 脚本 facade 中**：主会话可在 Workflow 外按 `android-dev` 技能运行预检、项目发现、构建安装、截图与 UI 自动化并记录结果；Workflow 脚本和子代理内使用已核验的 Gradle、ADB、SDK 命令做相同目标的验证，不假设子代理能调用主会话 MCP。无法执行的 MCP 专属检查如实列为未验证。SDK 许可、密码、真实发布签名、擦除 AVD/用户数据等需要用户才能完成的动作不得自动越权。

### 3. 产品与工程不变量

- **平台/架构**：Kotlin＋Jetpack Compose 真原生界面；Rust 是实际任务、日常实例、计时状态、跨日切片、时间修正与统计规则的可测领域核心，不是空壳；通过窄 UniFFI 接口。Kotlin 唯一掌管 Room/SQLite 写入、Android 生命周期、通知、时钟采样、文件与 UI；Rust 不直接写库或承载 WebView 界面。锁定依赖及 Gradle wrapper；只声明能构建并验证的 SDK/API/ABI，后续升级有迁移路径。进程重建/重复命令不得让两套语言各自产生不同业务事实。
- **任务**：临时未完成始终在今日日常前；日常在固定应用时区的每个本地午夜重现，不受前日完成影响，不积压漏做。新建日常当天出现；归档与完成独立；归档保留历史且期间无漏做，恢复原 Task ID 可续接；临时完成进历史，可重新打开原任务。标题历史在改名、临时完成和计时明细中保持当时快照；备注无历史版本。组内手动排序、完成日常折叠、过去日常可补记/撤销。
- **计时**：从卡片选择正向或自定义分钟倒计时，明确按“开始”才计；倒计时按 Task ID 记忆最近分钟，新任务 25。只允许一个运行/暂停会话；暂停不累计，结束保存实际投入；切换任务、计时中主动完成先确认；跨午夜连续运行并拆日；主动跨日完成让用户单选昨天/今天、突出今天。到点停止提醒，不自动完成；结果页可选休息或继续，继续须重新明确开始，休息不计时。普通锁屏和切 App 继续；异常中断推算段需接受/修正/舍弃，未确认不能进入统计。强制停止、关机及通知权限限制不得宣称必定准点响铃。
- **时间账本**：自动时间片、手动增加、某任务某日设为总量、事后编辑/删除均可追溯且幂等；按明确事件顺序重放，设总量之后新增仍累加，修改旧记录不偷偷改变顺序，跨日不重复计数。日期、周/月、任务占比和 GitHub 风格热力图来自相同聚合；手动记录只有日期和时长，不编造起止时刻。固定应用时区、手动变更预告、既有历史不重算、DST 23/25 小时及不同时区纪元必须覆盖测试。
- **备份与隐私**：离线无账号/同步；手动导出、本机滚动恢复点、可选密码；完整替换前验证并保护当前数据，错误密码、损坏、旧/未知版本和写入失败不改变现有数据；标准经审查的 KDF 与认证加密，不自创算法或硬编码密钥；未加密备份明确提示敏感性。本机恢复点不冒充跨设备备份。通知内容最小暴露；不上传任务名、备注、计时内容或把它们用于素材搜索。
- **视觉**：首版即有统一的原创/获授权艺术资源，不以占位图、随机网图、默认 Material 列表充数。按视觉提示词落地自有 Compose 设计系统、今天/记录/洞察/设置、专注页及所有空/满/错误/大字体状态；图片版权和可打包再分发权逐项留证。若无法合法取得外部插画，使用**实际原创**、风格成系列的矢量/Canvas 插画并做真机评审，不谎称获得第三方授权。图表精确且能以文字读出，拖动有单指/读屏替代；正文对比度、48 dp 主要触控目标、系统返回、减少动画与 TalkBack 语义不可遗漏。

### 4. 分阶段实施与每阶段放行条件

**阶段 A：规格确认、事实预检和实施方案。** 先检查是否已有用户对整份需求规格的明确整体确认；若没有，将可审阅的规格、与访谈回答的对照、设计默认清单、可辨识风险与冲突整理成交付包并停在此关卡。获用户真实确认后形成当前环境矩阵，确定 minSdk/targetSdk/ABI/NDK 与依赖锁定依据；画出 Room 实体/索引/迁移、Rust 命令和 UniFFI 类型、时间锚点、备份原子替换路径、UI 状态流。列出 AC-01–AC-20 各自属于哪个自动化/设备/人工检查。独立审阅者找状态竞态、回滚漏洞、已确认与设计默认冲突，修复设计后继续。若用户修订规格，先更新各文档再写产品代码。

**阶段 B：艺术设计和用户视觉审阅。** 根据独立视觉提示词产出可审阅的设计系统、关键页面与状态的高保真稿、动效与无障碍说明，以及首版艺术资源的原创/许可来源、可打包权和适配样例。先由独立代理检查图像权利、页面一致性、文字可读性和产品语义，修正后提交给用户整体审阅。**只有用户对设计稿与权利清单真实放行后才能进入产品代码实现**；代理互审、一个漂亮截图或 Workflow 运行确认均不能代替。若用户要求改动，更新设计稿并继续同一流程，原需求中已确认的美学优先级不能降级。

**阶段 C：可编译的 Android＋Rust 真集成。** 视觉关卡放行后创建完整 Gradle/Kotlin Compose 与 Rust workspace、锁文件、Gradle wrapper、Android 打包配置、UniFFI 生成与调用链，先交付能在隔离模拟器安装启动的垂直切片：UI 发命令→Rust 返回领域结果→Kotlin 事务持久化到 Room→重启后显示。构建必须加载真实 `.so`；静态假数据或永远不触发的 Rust 函数不算集成通过。借鉴 Now in Android、Jetsnack、Jetchat 的工程技巧需核对现行仓库许可，不复制整套页面。

**阶段 D：核心任务、计时与统计。** 先以 Rust 单元/属性测试固化任务新日生成、归档/恢复、标题快照、唯一计时器、暂停、DST/跨午夜、待确认异常时长和修正账本重放；随后 Kotlin/Room 文件库、迁移与事务接入，再做今天/详情/专注/历史/日历/周月图/热力图的完整可操作路径。阶段末执行 AC-01–AC-15 的可自动化部分，特别测试 20＋30→设 35→再投入 10＝45、旧记录编辑、同一命令重放、跨日一段只在各日计一次。若测试说明规格口径有矛盾，先改正确性再改 UI。

**阶段 E：Android 系统与备份。** 配置合法的前台运行、通知权限、提醒震动/可选声音、后台/锁屏、进程死亡/重启恢复。对每类系统中断记录实际表现，不把 force-stop 当作正常后台。完成 SAF 导出、应用内滚动恢复点、加密/明文选择、密码错误/坏文件/磁盘不足/迁移和完整替换的失败安全。用户数据相关变更只用合成测试数据；任何备份恢复、同包名升级、卸载/清除数据的测试都限定在专用测试包名与隔离 AVD 或全新测试环境，不覆盖已有模拟器上的应用数据；无隔离环境则该项验收受阻。

**阶段 F：原创艺术与真实页面。** 以阶段 B 经用户审阅放行的设计稿与授权/原创素材为唯一视觉依据，落地原生页面和细致动效、折叠/排序/确认/空态/异常态；编码过程中不可用临时占位图替换已审设计。截图检查不得只看程序化尺寸，也要人工评价层次、插画与文案关系、长标题和对比度。实际安装后用隔离模拟器/测试设备截图和 UI 自动化走通主要交互；若有真实 Android 手机，追加 TalkBack 和中端机性能/耗电验证。应用视觉不得因构建通过就自动宣布高级感合格。

**阶段 G：发布候选验收与修复。** 使用项目实际构建入口运行 `cargo fmt --check`、`cargo test`、Clippy、属性测试/有界 fuzz（Windows 不支持时在可用 CI/Unix 环境执行并如实标明）、Gradle 编译/单测/Android lint、文件 Room 迁移/备份测试、可用设备的 Android 仪器与 UI 测试；再执行接近发布构建的端到端流程与 AC-01–AC-20 覆盖表。不要用单元测试代替 APK 安装与前后台、用模拟器性能代替真实中端手机数据、用截图比对代替 TalkBack 手测。测试失败时给出失败输出、根因、修复及复测；真机、签名或许可条件不满足时其他工作继续完成，但该项验收标记受阻，不能宣称首版全部通过。

**命令门禁的编排方式**：上次检查仓库没有构建入口，本次仍需重新查证；在通过两道用户审阅关卡后，先由工程子代理创建 wrapper、Cargo workspace 与稳定测试命令，再由工作流脚本用**编译时写死的命令名称**（如 `world.run("cargo", [...])`、`world.run("gradlew.bat", [...])`，具体根据预检工具和路径决定）执行检查，根据 `exitCode` 判断。`world.run` 的命令不能由运行时变量拼接，运行参数可放在数组里；同一脚本可先检查文件存在性再进入对应阶段。子代理负责开放式实现/排错；在快速单测通过后，**至少运行一次完整、最强的可用集成检查**才能交付。对每个阶段设置有限修复轮次并以脚本中的明确条件结束；不因为供应商等待而递归创建工作流。不安装可疑包、不接受 SDK 许可、不改系统虚拟化配置、不清空用户 AVD 来让测试“通过”。

### 5. 完成交付与诚实报告

在工作区保留可构建的全部源代码、依赖锁文件、构建与测试脚本、必要的构建说明、素材许可/来源记录、合成验收数据及简洁的中文质量报告。输出**实际可安装的调试 APK** 的相对/绝对路径、文件大小与 SHA-256。AC-19 要在专用测试包名/隔离设备上用**同包名同签名的旧/新两个 APK**执行保数据升级：若只是从单次构建产生一个调试 APK，不算 AC-19；调试签名可用于隔离环境里的同签名升级实验，但不能凭此冒充正式发布签名或满足 P3 正式分发准备。正式发布包要求稳定管理外部提供的签名凭据、真实同签名升级演练；本提示词不授权生成、存储或泄漏生产签名密钥，缺条件须记为阻塞。不要自动把 APK 安装到用户真机；只有隔离模拟器或经明确指定的测试设备可用于自动安装。APK 若超出 Workflow artifact 的文件大小限制，主 artifact 发布中文交付报告并列出本地 APK 路径与校验值，不因 artifact 限制谎称没有 APK。

最终报告逐项写出：已实现功能与未实现功能；AC-01–AC-20 的通过/失败/未验证及证据、命令与退出状态；Rust/UniFFI/Room/Compose 的真实集成方式；设备型号/API/ABI 与截图/无障碍/性能实测范围；备份错误路径与数据保护证据；资源授权情况；安装和运行方法；当前阻塞以及原因。至少一次由未参与主实现的代理检查“功能遗漏、静默数据丢失、视觉不合格、未授权资产、结果夸大”，修复高优先级问题后再发最终报告。**终态只可三选一**：①“首版验收完成”：用户已放行规格和视觉稿、首版全部强制 AC 与质量门禁通过，包括 AC-19 同签名升级及 AC-20 真实中端设备证据，许可完整且 APK 可安装；②“代码完成、验收受阻”：功能已实现，但缺真实设备、签名/升级条件、素材授权或某项强制验证；③“实现受阻”：尚缺关键工程条件或实测失败未修复。Workflow 自身 completed 状态只表示脚本返回，不代表产品验收通过；不能把关键未验证项写进报告脚注后仍称“首版已验收完成”。若环境或授权阻断某项，不把它标为通过；能独立完成的部分继续推进到完成。任务收尾时仅在出现稳定可复用的运行命令、前置条件、已知限制或排障结论时更新根目录 `memory.md`，不写临时日志或普通测试通过结果。

**现在开始**：先读取依据并预检；依规则创建或复用匹配的 Workflow，提交脚本供用户确认运行。脚本首先执行规格审阅检查，已有用户整体确认才进入艺术方案与权利清单的可审阅产出；视觉经用户真实放行后再实施产品代码。遇到需要用户审阅的关卡，应以完整可核对的材料报告阻塞，保留文件与工作记录，等待放行后继续同一工作流或修订运行；不得把“停止等待审阅”写作永久放弃项目。其余阶段持续工作到交付物形成或出现只有用户能解除的阻塞。最终用中文、可点击文件路径和明确验证证据汇报，不用“后续自行实现”的建议代替已经放行的开发工作。
