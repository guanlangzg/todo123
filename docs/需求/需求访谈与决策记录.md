## 1. 文档职责与使用规则

- 本文是需求访谈及业务决策的可追溯记录；每轮新增问题和答案均在此更新。
- `AGENTS.md` 保存项目协作规则，根目录 `memory.md` 保存精简约束、稳定经验和本文入口；二者不能替代本文。
- “推荐”不是用户确认。“已确认”只来自真实用户回答，后台通知不属于回答。
- 没有回答的题目保持“待回答”；仅确认部分含义时，不能扩大成整套未明确的规则。
- 用户改变决定时，保留旧决定和变更理由，不静默改写访谈历史。
- 最终开发需求文档从确认决策中提炼，另外给出状态、数据、交互、非功能要求与验收用例。
- 当前不搭建应用，不编写产品代码，不注册、上传或发布到任何商店。
- 第四轮后用户明确停止业务细节追问，接下来累计最多 10 个开发路线选择，要求 Rust 类语言、尽可能原生、借鉴高品质界面代码库、严格质量要求；不以开发效率为优先。尚未确定的小规则由开发方给出明确设计默认，不伪称用户确认，不借此引入范围外功能。

## 2. 用户原始目标

用户希望创建个人使用的 Todo 软件，类似番茄时钟和计划清单软件，并要求先充分调研相关开源项目或已有软件，再形成非常详细的软件开发需求文档。通过分轮选择题澄清不确定点，每题给出多个选项与推荐。

原始核心诉求：

1. 美学设计必须高级、交互流畅，让用户有欲望使用。
2. 后期任务卡片可以手动设置或随机配置高清、有艺术感的插画。
3. 日常任务每天全部刷新，例如微信读书、记单词、LeetCode、看文献；不论前一天有没有完成，每天都要更新。
4. 临时添加的任务长期保留，始终排在日常任务前面，不随日刷新清除。
5. 记录每项任务的投入时间，类似番茄钟；有统计和日历查询每天时间投入。
6. 用户后续强调：高级感是首要要求，具体设计由开发方负责；统计页含 GitHub 风格热力图，视觉表现要丰富、有吸引力。
7. 用户要求项目添加 `AGENTS.md`、`memory.md`，且访谈问题必须有独立文档存储，区别于 memory。

## 11. 第五轮：Android 原生与 Rust 开发路线

### Q51 — 原生界面与 Rust 核心如何分工

**问题：**用户要求首发 Android、尽可能原生的高级艺术 UI，且 Rust 类语言真正参与产品核心。第一版采用哪条架构？

- B. Compose 原生 UI + Rust 同时拥有领域逻辑和 SQLite 数据库/迁移。Rust 独占持久化读写，Kotlin 仍负责 Android 平台能力；跨语言接口、迁移、打包和调试责任更重。
- C. 主要用 Rust 构建 Android 界面（例如 Dioxus 默认 WebView）和领域核心，接受界面不是 Android 原生控件，原生行为和质感需额外实测；这条路线优先 Rust 覆盖率而非原生 UI。

**当时推荐：**A。官方 [Jetpack Compose](https://developer.android.com/compose) 是 Android 原生 UI 工具包；[UniFFI](https://mozilla.github.io/uniffi-rs/latest/) 能生成 Kotlin/Rust 绑定，但本身不负责 Android native 库的编译和 APK/ABI 打包。Dioxus 的 [Android 支持及默认 WebView 渲染说明](https://github.com/DioxusLabs/dioxus#first-class-android-and-ios-support) 不能当作原生 Android 控件。界面高级感由视觉设计、素材、动效与设备验证决定，不能仅凭 Rust 语言承诺。

**用户回答：**“A. Compose 原生界面＋Rust 业务核心（推荐）”。

**状态与确认：**已确认 A。Kotlin/Jetpack Compose 拥有 Android 原生 UI、平台生命周期、通知、Room 数据库和文件；Rust 承担日常任务、计时状态、跨日分配、统计修正等可测试领域规则，经窄 UniFFI 接口连接。不以 Rust 持有数据库、Dioxus/WebView 界面或仅象征性使用 Rust 代替本决策。Q1–Q50 的业务规则不重开；用户要求严格质量和高级美学，门禁与视觉由开发方编入详细规格，不提供降低品质的选择题。
